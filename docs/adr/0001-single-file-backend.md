# ADR-0001：后端保持单文件，不拆模块

**状态**：已采纳

## 背景

`src/server/serve.ts` 约 4000 行，包含 HTTP 路由、39 个工具实现、LLM 代理、
技能市场、定时任务调度、记忆系统。任何常规工程标准都会建议把它拆成
`router.ts` / `tools/` / `api/` 这样的模块结构。

## 决策

**保持单文件**，不做模块化拆分。

## 理由

1. **这个文件是重建产物**。原 `serve.ts` 源码在 v7.0.0 打包时丢失，现文件是
   从 esbuild 产物反推重建的，风格为全 `var` + 大量内联逻辑。它不是按模块
   边界长出来的，而是在「先让它跑起来」的前提下还原的。
2. **拆分收益低于风险**。4000 行单文件的主要代价是「难导航」，而这是 grep
   能解决的问题。拆分的真实风险是：跨模块的共享状态（`sharedDb`、
   `globalWorkDir`、`PORT`、各工具间的隐式依赖）在拆分过程中极易出现
   循环引用或初始化顺序问题——这类 bug 只在特定请求路径下暴露。
3. **它跑在 Electron 主进程内**。任何未捕获异常都会带崩整个应用（不只是后端），
   因此改动需要格外保守。
4. **测试策略已绕过这个约束**。安全防护用集成测试打真实端点
   （见 ADR-0004），不需要把内部函数拆出来才能测。

## 影响

- 新增后端能力时继续追加到该文件，用注释分区（`// ─── 分区名 ───`）保持可导航
- 需要单测的纯逻辑**抽到独立模块**而非拆大文件：`src/shared/sensitiveOps.ts`、
  `src/shared/sse.ts`、`src/shared/chatModes.ts` 都是这样来的
- 若将来要拆，前置条件是为每条关键请求路径补齐集成测试作为回归网
