# ADR-0003：权限档位在代码层强制，不依赖提示词

**状态**：已采纳

## 背景

应用提供三档权限：「需要我确认」/「可以编辑」/「完全访问」。原实现是把档位
翻译成一句系统提示词——ask 档写「执行任何写文件、删文件、移动文件或终端命令前，
必须先用一句话说明将要做什么并等待用户明确确认」。

对本地智能体来说这是最要紧的一道边界：它手握真实终端与文件系统，能删文件、
跑命令、改代码。

## 决策

**在工具执行前加代码层闸门**，提示词作为补充而非唯一防线。

## 理由

1. **提示词不是强制手段**。模型完全可以不遵守，直接调用 `delete_file`。
   把安全边界建立在「模型会听话」的假设上不成立。
2. **同类工具的通行做法**。Claude Code 等工具都在代码层拦截危险操作并请求
   确认，而不是只写进提示词。
3. **需要一处唯一判据**。此前主对话与集群各有一份敏感操作判定，且集群那份
   漏判了 Windows `del /f /s /q`（正则要求 `/s` 紧跟命令名，而实际参数顺序
   任意）。两份实现意味着两套漏洞。

## 影响

- 判据集中在 `src/shared/sensitiveOps.ts`，`checkSensitiveTool` 是唯一入口
- 流式循环新增 `beforeTool` 回调：返回字符串即拒绝执行，并把该字符串作为
  tool result 回传给模型（模型会据此改方案，而不是静默失败）
- 档位语义：ask 拦不可逆操作；edit 放行写入但仍拦不可逆；full 全放行
- 新增危险模式时**必须同时加一条防误伤用例**——判据过宽会让工具变得不可用
  （如误拦 `git push origin main`），这比漏判更难排查
- 后端 `shell` 工具另有自己的黑名单（拦「绝对破坏」如 `rm -rf /`）；
  前端拦「局部破坏」如 `rm -rf ./build`。两者互补，不是重复
