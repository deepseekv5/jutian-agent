# ADR-0002：简洁度优先「去重复」而非「改结构」

**状态**：已采纳

## 背景

前端架构审计给出约 47 人日的改进清单，其中大头是拆分巨型组件
（SettingsModal 1285 行、MessageInput 1263 行、useChat 1081 行）与
重构目录分层。同时审计也发现大量「同一逻辑写多遍」的重复。

## 决策

**先做去重复，暂不做结构性拆分。**

## 理由

1. **风险与收益不对称**。拆巨型组件要同时改动状态提升、props 传递、
   渲染边界，一处出错就是整块功能不可用；而重复收敛是纯减法——把 N 份实现
   换成 1 份，行为可逐处对照验证。
2. **重复的代价是复利**。每多一份实现，就多一处要同步修的 bug。实际案例：
   - SSE 流式解析在 6 处各自手写，写法互不一致（`data:` 与 `data: ` 混用、
     `[DONE]` 有的 break 有的 continue、跨 chunk 半行处理不一）
   - 时间格式化 23 处各写各的（有的带 `hour12:false` 有的不带、
     有的借 `sv-SE` 拿 ISO 格式）
   - `uid()` 有 6 份内容相同、只差前缀的拷贝
   - 敏感操作判定在主对话与集群各有一份，且集群那份漏判了 Windows `del /s`
3. **重复本身会掩盖 bug**。收敛 SSE 解析时才发现原实现有一处用
   `chunk.split` 不累积缓冲，跨 chunk 拆开的行会丢——六个副本里只有这一个
   有此问题，不收敛就永远发现不了。

## 影响

- 新逻辑落地时先问「站内是否已有实现」；有则复用，无则抽到
  `src/renderer/utils/` 或 `src/shared/`
- 已收敛的共享点：`shared/sse.ts`（流式解析）、`utils/uid.ts`、
  `utils/datetime.ts`（时间格式化）、`engine/httpErrors.ts`（错误映射）、
  `shared/sensitiveOps.ts`（敏感操作判定）、`engine/toolLoopGuard.ts`（循环护栏）
- 巨型组件拆分留待有完整测试覆盖之后再做
